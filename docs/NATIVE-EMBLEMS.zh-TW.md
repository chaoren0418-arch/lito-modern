# 血盟徽章與現行正式協定相容性

本輪使用者要求恢復開發並補齊整體性。專案工作佇列已設為 in_progress，完成條件擴充到完整玩家流程、資源涵蓋、GUI／音效、Release 與長時間穩定性；整體尚未完成。

## 實作

- C30：非零 u32 徽章 ID，5 bytes。S35：ID＋384 bytes，完整 389 bytes；16×12 little-endian RGB555。只有原始 word 0 透明，0x8000 是不透明黑。
- 每個 World 的快取上限 512、未回覆上限 32；每輪 poll 最多送 4 個。5 秒無回覆標記逾時，仍在需要集合中的 ID 不自動重送；保留該 ID 時可以接受延遲回覆。未請求或重複回覆不加入快取。
- 新場景／角色重選／取消／失敗會清除快取。伺服器協定沒有請求 nonce；同連線重建世界後再次請求相同 ID 的舊／新回覆无法從封包本身區分，依伺服器 ID→圖像契約使用。
- 圖像接入實際世界合成器。位置自 #334（2026-11-12）起依原版：
  - 名字旁（489D15）：只畫**滑鼠指向的那個角色**，位置是名字列左 20 px、上 1 px（有徽章 ID 時名字本身右移 10 px）。自己的徽章也只在滑鼠指向自己時才畫，不再固定顯示在自己名字旁。
  - 頭頂（485F30）：盟戰背景啟用（原 834F14，對應 `World.relations.active`）時，actor+0x20 非零的角色（滑鼠指向者除外、隱身者除外）在角色位置 +17／−52 畫徽章；y ≤ 0 不畫。頭頂錨點沿用血盟標記的做法，用已插值的角色位置，不另加原版移動子格表。
  - 徽章不改變滑鼠命中 owner。靜態依據與未驗證項目見 `docs/reports/issue-334.md`。

## 正式版本變動

schema37 為 E5F2E01B。核對期間先觀測 595245C8，再觀測 EBF5EE66；均只讀來源、複製到本重建版。最新固定驗證副本為 EBF5EE66F051700AC4B8F524847D7372AF8065C4DBB5D91B2F74E03DADFF4E7B。

- S12 的 x/y 是起點，目的地是起點加 heading。改用正式 NativeMovement 產生八方向與自身校正向量；越界在修改 World 前拒絕。
- S0B status bit 0x04 需要額外五 bytes；保留不解釋的尾段，嚴格拒絕缺少或多餘欄位。正式輸出目前為 ff00000000。
- 房間目錄完整列仍可解析；新版另隱藏已開始／已結算房間及調整結算狀態。用實際 ClientSession 回歸確認，不把舊向量相同當成整體相容。
- E5 快照、舊角色／移動向量、class 清單及反組譯差異均保留在驗證紀錄。第一次新碼測試時來源再次更新，遷移檢查拒絕，因此舊角色 fixture 造成測試失敗；保留失敗記錄，修正快照與向量後重跑。

## 驗證狀態

實際執行結果以 `驗證紀錄/current/native-emblems/summary.json` 為準。`verify-native-emblems.ps1` 使用隔離 memory GameHub 與真實加密 ClientSession；只注入測試血盟／角色 metadata，由正式 C30 handler 查詢並回覆圖像。六個場景核對共用 ID 去重、替換、未知 ID 逾時、清除與像素。這不是玩家建立／上傳血盟徽章或正式 SQL 驗收。

定向 Rust 涵蓋所有 65,536 RGB555 word、所有截斷、尾端、32／512 上限、延遲與重複回覆、世界重建及 actor ID／metadata 切換。整體 GUI、實際聽音、全資源、多人及完整 Release 流程尚待補齊。

## 新版訓練對手缺口

EBF5EE66 的 startBattle 強制關閉舊訓練 bot。舊 combat probe 等待 actor 2，所以不能把 schema37 的 54 情境重新標成新版通過。第一輪實際連線暴露此問題，記錄保存在 before-visual-fixture。

徽章／名字／顯示狀態的純畫面 fixture 現在明確注入展示用 actor 2（非權威戰鬥對手），再使用真正加密通訊處理 metadata 與徽章。戰鬥、技能與結果場次需要建立第二個真實玩家連線，重新核對攻擊、HP／MP、死亡、結算、重入；這是下一個整體性優先項，不修改正式 JAR 來恢復假對手。
